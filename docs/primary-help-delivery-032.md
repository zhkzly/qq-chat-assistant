# Primary help delivery 032

This candidate removes the automatic foreground semantic critic from ordinary
manual-copy QQ assistance. Actual preceding runs showed that the critic could
misread correct suggestions and add misleading private corrections even when
its output was explicitly labelled fallible. The selected-model primary help
remains subject to independent behavioral evaluation; removing criticism does
not make a bad primary response acceptable.

## Actual product path

```mermaid
flowchart LR
  R[Scoped original history and memory] --> C[Current intent and context assembly]
  C --> M[Primary selected-model help]
  M --> A[Material and option admission]
  A --> T[Terminal deliverable validation]
  T --> S[Mechanical publication seal]
  S --> V[Scope, source versions and artifact availability]
  V --> P[Atomic persistence]
  P --> U[User edits or copies manually]
```

An explicit request for analysis or review is normal primary help. Ordinary
responses have no `fidelity_check` POST, automatic semantic veto, regeneration,
review metadata, warning or verified badge. Lookup, genuine structural repair,
compaction and background memory maintenance remain real counted operations.
No other model, classifier, background critic or hidden replacement is added.

## Mechanical publication integrity

`src/publication-seal.cjs` uses the existing canonical candidate field table for
visible text, explanation, message style and option labels. It also captures
object/array identities and transfer/disposition fields such as kind,
replyDisposition, requestDelivery, blockers and response-recovery mode. A
canonical-operation WeakMap entry alone cannot establish that content is
unchanged.

The seal binds completed producer payloads and input identities. Its source
revision union includes primary, admission, options, earlier request and
compaction-root references; conflicting source revisions are rejected rather
than silently upgraded. Current control sources must retain their captured
versions. Generated artifacts retain separate dependencies and the existing
artifact availability resolver; their identities are not treated as raw world
facts.

The controller checks the seal, raw source versions and artifact availability
before publication and again inside the atomic publication, including just
before appending the response. Existing current-request checks cover account,
contact, QQ revision, private input sequence, model and context generation.
Legitimate topic/state writes in the same transaction do not count as an
external stale-request event. Mutable debug fields added after generation are
not mistaken for immutable producer inputs.

The seal adds no model call or context expansion. Its receipt is an integrity
fingerprint with `semanticCheck:false`, not a semantic certificate. It does not
reuse the previous audit context builder or its full-original expansion and
request-budget failure path.

## Preserved boundaries and limitations

- Program material/reference admission, exact current fact spans, selected
  option tuples, exclusion, withdrawal, source versions, artifact availability,
  account/contact isolation and cancellation remain mandatory.
- Drafts, adoption and clipboard actions remain distinct from actually sent QQ
  messages. This change does not implement sending, forwarding or auto-reply.
- Historical semantic-review metadata stays readable through its existing
  Store/UI/projector path. Its source/leaf invalidation and private-copy cleanup
  remain compatible. Ordinary new help does not create that metadata.
- Primary suggestions can still fabricate, misunderstand a request or sound
  awkward. The removed semantic defense was fallible; no zero-leak, factual,
  naturalness or relationship-outcome guarantee replaces it. Actual behavioral
  failures must stay visible to independent review and later Goal iteration.
- Existing compaction literal-quote fragility is unchanged. A long conversation
  can still stop before foreground generation if `quoteRefs.text` is not an
  exact continuous original span. That is a separate follow-up, not repaired or
  hidden by critic removal.
- The initial context compiler, model/provider, raw cases, criteria, rubrics,
  project roles, hooks and approval settings are unchanged.

## Verification scope

The implementation's native probes exercise one-primary ordinary help, normal
user-requested review, real structural repair and lookup, post-parse candidate
and reference mutations, source revision/forgetting, account/contact/cancel,
generated editing-artifact withdrawal, and legitimate topic/state writes in the
same transaction. Pure seal probes cover all canonical visible fields,
transfer/disposition flags, input identities, source-union conflicts and separate
artifact dependencies.

Older functional fixtures that awaited a removed critic were migrated to the
actual pending-primary or bindPlan/atomic publication boundary. Genuine source,
permission, artifact, continuity, feedback, budget, no-send and independent
report-only-gold assertions remain. Former ordinary-review fixtures now assert
that no unrequested reviewer is invoked; historical stored-review tests still
exercise actual forgetting, correction and leaf/draft cleanup. No fictional
passing semantic rating is created by these migrations.

The first all-file collector retained partial logs from an obsolete fixture
waiting indefinitely for a critic. Bounded diagnostic collections retained
failures and timeouts; those are not passing evidence. The final complete
functional collection is separate. Full synthetic replay proves integration
only; selected-model comparisons and independent output review belong to the
coordinator. No live/provider call, semantic self-grade, commit, merge, QQ
restart, activation or production database write is performed by this
implementation task.
