# 上下文与记忆整体重构提案

状态：设计提案，等待根代理裁决；本文件不代表重构已经实现或效果已验收。设计基准为 [整体重构方向记录](relationship-assistant-refactor-note_CN.md)。本阶段只新增本文件，不修改运行源码。

## 1. 要改善的行为与当前缺口

用户想和有好感的人自然地熟悉、表达自己、了解对方并创造双方愿意的相处机会。因此，上下文系统的产物必须让规划器看见**这次具体有什么可聊、哪些表达确实属于用户、哪些旧事已经变更、哪些方式仍适用**。目标宽泛的长期 goal 不能独自承担材料检索和交流选择。

目前 `assistant-context.cjs` 已超过 900 行，混合了原始来源投影、跨来源排序、私下讨论指代、话题与记忆整理、媒体、方法卡、预算回退、授权和成稿隔离。新增一条加载规则会影响多个后面的回退循环。只把函数搬到几个文件，仍会留下同一份可变 payload 在多处隐式增删的问题。

保留现有已经有消费方的能力：SQLite 原始来源与增量 journal、来源版本校验、实际收发标记、typed claims/events、局部 topic、私下讨论压缩、有限 lookup、模型请求账本、图片来源绑定。重构其职责与调用关系，而不是另建一套 Jev 服务、第二份记忆库或逐历史消息调用的语义控制模型。

功能基线、冻结的 17 次 HTTP 及其独立语义评审用于寻找回归和薄弱环节，不能替代新架构的验收。尤其应区分“资料未提供”“有材料但选择成机械收尾”“规划正确但成稿丢意图”“模型本身表达不佳”。

## 2. 数据职责：原话、长期记忆、当前任务、可聊材料分开

| 对象 | 唯一职责与消费方 | 写入、有效性与禁止事项 |
|---|---|---|
| Source ledger | 保存实际 QQ、用户主动私下原话、用户资料和反馈；为所有派生对象提供可核对根来源 | QQ 原 ID 始终为字符串；实际发送仅来自真实 outgoing。原始事件时间与本地到达顺序都保留。撤回/排除产生失效信号，不以摘要复活原话 |
| Durable memory | 保存值得跨会话保留的有据事实、情节、明确稳定表达偏好；为 core/catalog/lookup 提供摘要 | 依赖 source revisions，标明主体、证据性质、历史时间与适用性；不把“说过”升级为当前仍成立。推测、未知与明确事实分开 |
| Consultation task | 保存当前小目的、表达方式、局部纠正、选择与未完事项；供规划及候选生命周期使用 | 从用户当前原话取得控制权；单次反馈不变永久偏好。结束/取消撤销本任务控制，QQ 变化不替用户重写目的 |
| Material catalog | 将真实来信、自我材料、共同话题、旧细节和安排组织成可用输入；供交流规划选择 | 派生读视图，不另存“她喜欢我”等状态。每项保留 owner/use/time/source availability；摘要和引用不自动授予分享许可 |
| Generated artifacts | 保存私下解释、表达选项、成稿、编辑与评价对象 | 独立于 source ledger；自动产物未经显式引用不反馈成下一轮事实、用户意图或未结束任务 |

长期 goal 描述用户的关系方向；task 描述这次想做什么；method 描述如何帮助；material 描述具体有何内容。四者不互相代替。没有新鲜自我近况时仍可从她的真实分享、共同话题、已知旧细节或开放认识提出切口；不要求用户先填一个小目的，也不能捏造用户的生活。

## 3. 常驻、近期、冷历史的生命周期

### 常驻核心

常驻的是小而有据的摘要与控制，不是全部人物档案：长期 goal；明确生效的表达偏好；少量有原始来源支持的长期事实/重要关系边界；当前 task 的目的、方式、局部纠正与必要指代。

核心事实携带 `subject / assertionKind / evidence time / applicability / sourceRefs`。例如虚构的“八月曾在书店帮忙”可辅助回访当时的阅读经历，不能改写为“她现在仍在书店上班”。来源失效立即使核心失效，不能等下一次后台 LLM 整理。

核心有字节边界且按用途组织。超过预算的完整摘要进入目录，不从原文任意截出一个看似确定的结论。对目前不适用的局部限制不设永久禁令。对于有当前反证的旧核心，反证与变更状态优先于原先稳定程度。

### 近期背景

72 小时是可配置、可检验的候选范围，不是质量结论，也不是把全部三天原文设为必要输入。范围同时包括实际 QQ 和用户主动私下商量；自动观察产物不属于用户主动商量。

近期候选按来源事件时间进入。当前回合另按交流连续性、真实引用关系及实际收发识别。三天前说过的话不会因为被加载就成为本轮来信；一次早先的告别也不自动禁止今天用户主动联系。

加载单位是完整原始消息、连续交流段、完整用户纠正及其必要指代。预算充足时，多段 72 小时背景都可以进入，不能靠最近 24 条或最后六组硬截断。预算不足时，保留当前任务与纠正；对其余段给出可查原始 ID、时间范围及遗漏数量。旧助手长解释可保留指代句柄并按需取回，不得挤掉用户完整原话。

### 冷历史

原始冷历史仍保存在本地。前台先读取有界目录，包括来源类型、日期、主题词、派生摘要、可取回 ID 和可用性。查找内容可以来自旧工作、兴趣、共同经历、原安排的取消/改期、讨论过的具体表达。

已有检索的有效排名必须保留，不能再用一个更弱的 literal match 将高相关结果打回。另一方面，初始 query 必须来自这次实际交流、当前请求与适用私下方向，不能把最近两条六十天前的无关私下原话无条件拼入查询，再把旧结果的高 score 解释为当前相关。

检索分数只是一条召回线索，不是事实可信度、人格匹配或关系好感分。明确的更正、撤回和反证从依赖/更新索引闭包取得，不以与旧摘要词面不一致为由滤掉。

## 4. 写入、冲突、更正与撤回

后台写入继续走已有增量 journal 与批次 receipt。累计来源、空闲时间和请求预算触发整理；不为每条新消息单独调用模型，不在用户等待建议时先扫描全部历史调用 Jev。

1. **实际新消息**：原话与身份先落原始账本，更新时间线版本；当前旧候选随实际收发按生命周期规则失效。记忆整理可稍后进行，当前规划仍能直接读到新原话。
2. **用户纠正**：当前任务先取得这次完整原话与新的待解释意图版本。旧事实/方式的纠正不等后台维护；若同时要求长期记住，才进入相应的明确持久化动作和回执。
3. **记忆整理**：模型提出 claims/events/items 的变更，程序校验来源闭包、当前 source revision、scope、批次完整性和 expectedVersion，事务提交。辅助整理失败不能丢掉可读帮助，也不能声称状态已整理。
4. **事实冲突**：原始两边证据都保留；分别判断说话主体、原话时间、有效时间、是否只是猜测、是否真的取代了同一命题。旧消息补采的到达顺序不能逆转较新的取消或职业变化。不能仅建立一条 CONTRADICTS 关系就宣称已经解析当前偏好或事实。
5. **撤回/排除/删除**：先由本地依赖检查使 core、topic、压缩、图片、候选及评估产物失效或降为待核对，再异步整理。撤回的内容不得从旧摘要、备份式候选或压缩 quote 恢复出来。
6. **反馈**：对某次建议的“太正式”先作用于该任务/表达；明确“以后都用短句”才成为稳定控制。复制、采用和实际发送分别保存；对方后来友好回复不构成某个方法造成亲近的因果证据。

这不是增加一套新的状态机：原始写入、memory batch、topic action、候选失效各有已有 owner。需要补足的是它们统一暴露的版本和失效依赖，避免 builder 同时承担写入裁决。

## 5. MaterialView：上下文要给规划器可消费的内容

本地 `MaterialView` 由已有来源字段组织少量输入项，而不引入逐项 LLM relevance 调用。

| 材料类别 | 输入依据 | 帮助规划器决定什么 |
|---|---|---|
| 当前实际交流段 | 原始 incoming/outgoing、引用、时间和图片可用性 | 她具体在分享或问什么；用户实际已说过什么；还有哪一处内容可回应 |
| 可分享自我材料 | 当前明确原话、允许分享的用户 note、已校验选中原文 | 用户确实愿意表达什么；不能以她的经历或旧习惯编造用户本周计划 |
| 近期共同话题 | 72h 来源段、当前 topic 的真实来源 | 已有细节中哪一处可继续了解；是否已经实际问过/答过 |
| 可回访旧细节 | 有日期的 core 与冷目录、必要 lookup 结果 | 某件旧事是否值得回访；哪些当前状态未知，哪些只是历史故事 |
| 实际安排及变更 | 邀请/接受/改期/取消/发生的完整来源链 | 能否聊安排进展；不能复活已取消约定或把提议当已发生 |

输入项可以使用现有语义：`kind / owner / use / sourceRefs / availableAs / time / applicability / relatedChangeRefs`。它们是本地的材料分类与证据可用性，不是程序猜测她的情绪或兴趣。

“已回应”也先提供可核对事实：实际 outgoing、引用关系、当前时间线位置及已保存任务进度。只有明确原话和实际观察能确定已完成；没有搜到回复不等于她不愿聊。语义上的重复判断由本次规划结合这些证据完成，不能仅用关键词或“最后一句是我发的”统一决定等待。

**不强制新增模型输出 `focusDetail / interactionMove / alreadyAddressedRefs`。** 这些字段若只是复述来源就没有独立消费意义。实际交流选择可继续体现在已有 `draftPlan.guidance.objective / allowedApproach / avoidances` 和其 sourceIds；需要表达的原意继续由授权 quotes 承担。候选版本可绑定已校验 plan 的摘要，而不让模型为了状态字段填空。

## 6. 分阶段 context views 与 JIT 流程

| 阶段 | 默认能看见的内容 | 必须排除或不能赋予的权力 |
|---|---|---|
| Planning view | 当前请求、真实位置、常驻 core/偏好、task、近期材料、必要旧证据、有界目录、少量适用方法 | 助手旧产物不能成为事实或用户新意图；goal 不自动授权自我披露；模型不声明发送成功 |
| Lookup replay | 原 planning snapshot 加本次取回的完整来源及后续变更、lookup receipt | 不能用检索包装提升原资料用途；模型请求的 ID 必须属于当前 scope 的可查询集合 |
| Wording view | 获准 quotes、必要实际 QQ/媒体、已校验短 task 控制、表达偏好投影和当前机会所需事实 | 无完整 privateConversation、私人动机、全量人物档案或长期 goal；不能更新记忆、权限和任务 |
| Review view | 用户指定问题/时间范围的原话、实际发送、反馈对象、正反证及覆盖信息 | 不以草稿采纳率或回复数量等同关系进展；不把空检索当没发生 |
| Recovery view | 同阶段不可变快照、必要来源与明确修复目标 | invalidResponse 仅为诊断；不能因恢复而新增披露许可、丢失意图或改用另一个联系人上下文 |

建议前台路径：

1. 捕获 scope、观察时刻、真实时间线版本、用户意图/控制版本、goal/topic/memory 版本及本次模型绑定。
2. 本地策略生成候选集合：当前必要内容、常驻核心、近期片段、相关目录；解析完整来源依赖与变更闭包。
3. 生成 `MaterialView` 后，按完整请求预算选择载入单元；必要来源不完整则明确缺口，不任意裁断原文。
4. 通过同一次 main planning 选交流内容与表达方式。有足够依据时直接给可成稿 plan；只有会改变这句话真实性、重复性、当前安排或披露范围的缺口才 lookup/澄清。
5. lookup 优先取具体来源 ID、时间段或带主题词的有界历史，并同时取相关更正/取消；复用现有最多两次查找与同一请求账本。
6. 创建受限 wording view，再生成完整可编辑表达；采用前复核 scope、timeline、用户控制及来源依赖。

JIT 是对具体缺口的补充，不是每次先走“检索→关系分析→关系阶段判断→用户问卷”。例如旧职业是否仍有效不妨碍回应她当前明确分享的阅读内容；用户本周真实计划未知，只限制那段自我披露，不能令所有交流方向停摆。

## 7. 可落地的模块边界

保留 `src/assistant-context.cjs` 和 `src/context-task.cjs` 的现有公开导出作为兼容 facade。内部模块不修改 store、不调用真实模型、不发送 QQ；写入和执行仍由各自 owner 处理。

| 新模块 | 单一输入/输出职责 | 不应承担的事情 |
|---|---|---|
| `src/context/snapshot.cjs` | 从 read port 捕获 scope/版本与不可变来源集合，提供规范 source/QQ 元数据和精确依赖读取 | 不决定聊什么，不维护新偏好，不遍历全部历史执行语义评估 |
| `src/context/policy.cjs` | 当前回合、近期候选时窗、core 资格和各阶段加载规则；版本化纯策略 | 不用 goal 预测她的心理，不将默认时窗宣称为最佳值 |
| `src/context/catalog.cjs` | 常驻摘要、近期段、冷导航和既有检索结果的读视图；暴露更新/反证与 availability | 不提交 memory patch，不把排名当可信度 |
| `src/context/materials.cjs` | 把已分工的资料组织为规划可消费材料，保留主体、用途、时间、来源及具体缺口 | 不编生活、不猜好感，不新增方法调用或强制输出义务 |
| `src/context/selection.cjs` | 按载入单元及依赖闭包进行预算准入，输出不可变 selection plan 和遗漏导航 | 不再多处直接增删同一个模型 payload，不吞掉显式选择或新纠正 |
| `src/context/planning-view.cjs` | 将选中资料、task、材料和方法拼成 planning/review/lookup view | 不校验可发送授权，不顺便写永久状态 |
| `src/context/wording-view.cjs` | 校验 quotes、来源用途、当前 task 控制和偏好投影，构建受限成稿 view | 不自己检索全档，不接完整私下理由，不写事实/状态 |
| `src/context/budget-manifest.cjs` | 通过注入的 request measurement 测量真实序列化信封，生成选择理由、来源版本和阶段 manifest | 不隐含放宽预算，不复制全部原文到第二份模型字段 |

公开 facade 只做参数兼容、默认 adapter 注入与模块组合。`buildContext`、`buildDraftContext`、`expressionOptionsFor`、`sourcesFor` 等已有调用方不需要同时更换接口。`provenance.cjs`、Store 的 source/CAS/批次校验继续是唯一权威；新模块复用这些守卫，不另写一份宽松版本。

读 port 可以先封装当前 Store 的同步查询，再按日期、来源 ID 与 summary inventory 优化读取。模型阶段不持有可写 Store 引用。精确来源读取必须与捕获版本相符；若读取过程中更新，快照重建或本次结果废弃。不要为了“快照”先复制所有原始历史到内存，也不要以最后一次数据库查询的版本冒充整次请求的版本。

## 8. 版本与候选交接：和工作流组件的接口

根代理已裁决采用程序拥有的 `QQ revision / privateInputSeq / validatedPlanDigest` 作为候选 fence。由 context manifest 输出实际读取的 source revisions、memory/topic/goal 版本和策略版本。`contextGeneration` 可继续做兜底取消，不能独自定义候选的语义新鲜度。

用户新私下输入先撤下旧主候选并保留历史/编辑；不能继续伪装为已经核对这次纠正的当前主候选。新的完整成稿发布为当前候选。纯解释只保留在私下历史，用户仍可取用原编辑稿，不自动恢复旧主候选。

模型不得只凭一个问号决定解释或纠正。“为什么总那么直白？”可能兼具两者。若含义仍不确定，可保留候选为待核对状态并给有用解释；不需要把所有输入都升级长期偏好。

`validatedPlanDigest` 从已校验 guidance/quotes/实际回复重点确定；它不表示实际发送。拒绝要求模型填写 intent/no-change receipt，也不凭模型声明恢复旧主候选。后台记忆整理不能抹掉用户独立编辑稿。

## 9. 交叉质疑与分歧记录

以下均为设计反例，非用户真实聊天记录。

| 讨论对象 | 具体反例/质疑 | 当前回应与剩余裁决 |
|---|---|---|
| 产品/工作流代理 → 上下文 | 昨晚书店话题已告别，今天用户没有新近况却想联系，不能先等长期记忆或目的问卷 | 同意。72h 具体材料足够时直接规划；昨晚收尾仅约束昨晚 episode，手动意图可启用新的具体切口 |
| 产品/工作流代理 → 上下文 | 私下改成含蓄稿后再问“为什么”，不能又推旧直白稿，也不该把新含蓄稿永久清掉 | 原提议 no-change receipt 自动恢复被根代理否决。采用程序 fence；新输入撤旧主候选，纯解释保留历史和编辑取用，不自动恢复 |
| 上下文 → 产品/工作流代理 | “为什么总那么直白？”同时可能是解释与纠正，若只看问号就会保留错误稿 | 不能用简单入口/标点决定语义。程序收到新输入即撤主候选；只由新完整成稿发布，而不依赖模型声明 no-change |
| 上下文 → 产品/工作流代理 | 用户从聊游戏改成散步，但 topicPatch 尚未保存，单绑 topic/opportunity 版本会让游戏句继续 primary | 用立即推进的 privateInputSeq 和已校验 plan digest，不能只绑定已保存 topic 版本 |
| 上下文 ↔ 质量代理 | 60h 前“别再问游戏”所在段过大，能否为旧游戏兴趣继续发问？ | 若是本轮 local 限制，不升永久 ban；若为明确持续边界/纠正，完整来源与必要指代优先。缺口只约束相关机会，不能全局停聊 |
| 上下文 ↔ 质量代理 | 八月书店工作 core 会不会把今天所有建议都变成“还在那上班吗”？ | 不应。历史事实携日期、当前状态未知；可谈其真实阅读经历。需要断言现职时才补依据 |
| 质量代理 → 上下文 | 后来明确说旧店关了、现做客服，仍回头核对旧工作会机械且忽略更正 | 同意。更正闭包覆盖旧现职解释，保留历史；围绕当前分享，不重复问已经明确的事实 |
| 质量代理 → 上下文 | 对方问用户本周末安排，已有资料只有她的喜好和用户一年前习惯，core 丰富也不能编当前计划 | 同意。主体与时间有效性限制那段自述；必要时私下问当前事实，同时先给真实可回应部分 |
| 上下文 → 质量代理 | 有 sourceRefs、JSON 和 candidate 仍可能只复述感叹或凭空补经历 | 同意分离机械/语义验收，不能以 schema 通过抵消内容选择或真实性问题 |

工作流代理已接受两个追加反例并同步根裁决：不按问号分类，不仅绑定已保存 topic，不用模型 receipt 恢复候选。其 OpportunityView 先提供需要处理的实际问题/分享及用户真实素材，再给可选展开，unknown 不是必须逐项问用户的槽位。

已否决方案保留以上记录，实施按 canonical note 裁决。core 优先级/时效与目录显示仍以已有来源、用途及可检验策略决定，不通过隐式默认塞进 builder。

## 10. 落地与验收边界

这是完整重构的一套内部实施顺序，不是向用户分批交付 MVP：先固定 source/版本和读 port，提取 policy/catalog/selection；再将 planning 与 wording 视图拆开并接入 MaterialView；最后将候选生命周期与后台维护依赖连通。根代理整体验收和集成前不激活真实应用。

保留基线所有来源、权限、预算、图片、引用、恢复和 scope 测试。新增/扩展的验收应有明确消费者与反例：

- 当前 actual → 材料 → guidance → 草稿的每条交接能定位丢失点；不只检查字段存在。
- 40 条跨三个近期片段、54h 用户商量、72h 边界移动、超预算完整段遗漏、显式旧 lookup 与长期 core 撤回都分别验证。
- 来源改口、旧消息补采、取消安排、局部限制结束和稳定偏好撤回不能被 core/压缩/目录复活。
- 同 Store 连续经历 incoming、实际 outgoing、新 incoming、用户纠正和“为什么”后，候选 fence、当前发布、历史与编辑对得上；纯解释不复活旧主候选。
- 不同 context views 在同模型条件下对照，独立评审具体帮助、自然表达、真实自我内容与可展开性；允许合适收尾、无问号和关键事实澄清，不为提高消息数量打分。
- 观察故障点后只修其 owner；不能因为一条句子不好，就增加更多核心字段、加载更长历史或新增一次模型判断。

任何“新架构已改善聊天”的声明都需要实际消费链与冻结语义结果。模块数、功能绿灯、上下文变短、token 减少、记忆增加或采用某论文术语都不能单独构成该结论。
