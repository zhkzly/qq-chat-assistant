# 本轮表达要求优先级与连续聊天验收

本次按用户确认的范围修复两处交接问题，并增加连续聊天验收。目标是让参考表达保留用户当前想说的意思，减少已经纠正后仍沿用旧要求的情况；不以口吻标签、消息数量或结构化输出成功代替实际帮助质量。

## 实现

- 普通偏好笔记、已审核核心偏好和配置先统一投影，再按本轮真实用户或规范反馈中的明确要求处理冲突。已有的长度、表情和直接程度三个维度参与归并；其他不冲突的要求保留。归并只影响当前请求，不更改长期记录。
- “不要短句”“不要太含蓄”等负向要求可以解除旧默认，不强制新增长篇或直白表达。清除本身也保留来源版本，便于追溯和请求重建。
- 受限成稿的`style`和`presentation`同步核对：已解除短句时不再携带`short`；仍有效的不加表情要求不会同时携带`useEmoji:true`。允许表情不等于强制使用表情。
- 新的本轮解析采用保守的表达指令形式。第三方转述、成对引号、Markdown引用整行、条件和私人理由不取得更高优先级；普通的“她表达很含蓄”“今天做了简短汇报”是素材，不变成用户口吻。自动观察生成的合成请求也不充当真实用户改口。
- 正常生成和结构修复对目的、口吻、待发送素材使用同样的说明。求助目的与分寸通过有来源的短指导交接，真正要分享的内容仍需授权片段；旧私下原文未经授权仍会被拒绝，调用上限没有增加。
- 上下文版本升级为`relationship-context-2026-10-17.3`，避免复用此前的缓存产物。没有新增口吻菜单、模型、运行时评委或数据库格式。

这是对已支持表达维度的局部修复，不是通用自然语言风格理解器。模糊要求及当前交流动作仍由规划模型结合原话理解；本次没有把“明确邀请”机械等同于某种口吻，也没有推断对方意愿。

## 验证边界

新回归使用真实Store、Controller、上下文构建与模型运输代码，数据和模型响应均为合成。覆盖note/core/规范反馈、负向清除、第三方及普通描述、引用、来源版本失效、请求重建、一次覆盖后恢复旧默认，以及坏结构计划经一次修复后进入成稿。它们证明交接和权限边界，不证明措辞自然。

交叉审查补出了Markdown引用在逗号拆分后逃逸的问题，先复现再修复。全量回归还要求修复说明显式保留“当前明确的表达控制”；补回该义务，保留原断言。没有通过弱化原功能要求来接受新输出。

实际模型验收使用事先固定的[三个连续虚构场景](style-priority-scenarios.md)：当前工作与旧活动的选择、明确邀请覆盖旧限制、真实保存偏好后的一次覆盖和第三方引用。每批上限18次HTTP，首次运输或HTTP错误即停止，不反复生成挑选好句。脚本来信只是测试条件，不是现实关系结果；真实保存需核对applied回执，不能把一条旧私下话当作已保存偏好。

## 实际结果与未通过部分

96个测试文件共655项功能检查、递归语法及diff检查通过。预声明连续批次使用现有配置及响应报告的`gpt-6-sol`，15次HTTP完成7个生成步骤；批内源码和设置不变。未参与实现、未读取源码的独立agent将7条候选文案评为可用，未见明确事实或含义硬失败，也指出多条仍采用“接细节加提问”的相近结构。该结论不证明稳定提升或现实关系效果。

必须保留的负结果是：S3第一次保存偏好的回执只有`pending`，没有`applied`。模型的取证片段省略了前面的“请记住”，程序按现有授权规则保留为待核对提议；本次没有放宽该守卫。因此原批次没有验证“默认已保存、临时覆盖后再恢复”。不能因最后一句简短且无表情就将它算作通过。

为单独验证本次代码修复，在保留原结果后，追加一次明确分开的合成Store播种检查：直接保存已知旧偏好，再使用同一冻结源码和同样本轮要求进入实际模型成稿。只用2次HTTP，旧偏好确实进入规划、本轮成稿不再携带冲突默认、原偏好正文未变，独立文案评审可用。它不证明模型完成保存，也不替代原批次未覆盖的恢复环节。两部分合计17次实际HTTP，没有重采样挑选句子。
