# Manual-help delivery and sparse semantic audit

Candidate 030 separates two responsibilities that candidate 029 combined into a
mandatory exhaustive proof: program authority over a candidate and a fallible
model's semantic review of that candidate. This is a manual-copy conversation
assistant. It does not send QQ messages.

## Supported cause

The retained selected-model 029 captures contain normal HTTP 200 responses but
frequent non-delivery: a 14-statement field violates a 12-statement census limit;
private interpretations and explicit conditional advice become unverifiable
world assertions; invalid optional material metadata consumes the sole repair
before a malformed checker report; and an actual fact is not the permission
sentence that refers to it. Fixing individual census types did not resolve this
common dependency.

`tests/fixtures/semantic-audit-029.json` retains four exact fictional checker
captures, their candidate/evidence/roles/revisions, raw response and original
transport/run hashes. These are diagnostic source evidence, not human references
or expected answers. Older 028 capture and census decoder tests remain explicitly
marked as historical compatibility contracts.

## Product behavior

The native checker uses `sparse-defects-v1`. It reads the actual candidate and
original evidence, and reports only concrete defects with an exact candidate
path/quote. Source contradictions, missing factual qualifications and private
sharing findings require exact original witnesses; candidate contradictions
require a distinct exact candidate statement. Unsupported personal events and
concrete question premises can still trigger one bounded whole-answer
regeneration and recheck. A malformed adjacent item or optional reason cannot
erase a valid concrete finding.

The checker no longer enumerates and certifies every sentence. Advice, ordinary
questions, interpretation, style and private conditional examples are not
required to satisfy an assertion taxonomy. Unknown or malformed findings stay
recorded as incomplete diagnostics. A transport or formatting failure does not
consume another checker-format repair. The request's original HTTP ledger and
single shared generation/structural-repair allowance remain in force.

A separate frame-bound delivery receipt is required before publication. It
rechecks the same candidate, original evidence, account/contact and versions.
The native sparse result never receives `approvalFor(allow)`, and an empty defect
list never means exhaustive verification. The actual stored/public status is:

```
semanticReview: {
  status: "reviewed" | "incomplete",
  candidateHash,
  bindingHash,
  exhaustive: false
}
```

An incomplete audit is visibly labelled in the assistant thread: `建议已生成；本次内容核对未完成，采用前请确认具体事实和私下信息。`
The user can still edit/adopt a suggestion and manually send it. A valid concrete
blocking defect remains blocking when regeneration is unavailable. No confirmed
bad candidate is released as an incomplete fallback.

Cancellation, changing account/contact, source revisions, withdrawal, invalid
artifact references and program material exclusions remain hard boundaries.
Source/current-context checks run again after the checker and inside the atomic
publication. Such failures never become semantic-audit uncertainty.

## Narrow fact and permission spans

A primary material selection may now include `factQuote` and `permissionQuote`.
Both are optional exact, nonempty spans: the fact must occur inside its selected
material, and permission inside the separately offered human authority. The
program restores source/revision identities and a separate material/referent/
permission binding. The reviewer sees the binding alongside complete originals.
Selecting a permission sentence is not selecting a fact; selecting one fact
never grants another private fact from the same source. Full negation,
conditions, newer exclusions and original roles remain relevant. No keyword
permission detector or persistent source-wide grant is added.

## Evidence limits

Program material admission validates declared material selections. It cannot
mechanically prove that every generated word uses only those selections. The
sparse reviewer can miss or misclassify a factual or privacy defect. This change
therefore claims no zero-leak guarantee or factual certification. Incomplete
review is an explicit manual-review state, not a passing quality grade.

Functional tests and synthetic browser/replay checks establish implementation
and lifecycle behavior only. Selected-model replay, independent actual-output
review and any desktop activation remain the coordinator's separate work. The
Goal, raw evaluation cases, behavioral criteria, rubric and project roles are
unchanged. No other model/provider or real QQ/credential dataset is used.
