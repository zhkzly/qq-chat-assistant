# 围绕关系目标配置上下文与压缩

目标是帮助用户与网上认识、有好感的女生发展成双方愿意的恋爱关系。系统应支持商量、回应、活动、邀约、表达好感及暂缓；判断依据是忠实帮助用户处理当前关系决定，并根据真实互动修正。生成、采纳或测试通过都不表示对方喜欢用户。

## 三个需要回答的问题

1. 哪些内容保证这轮商量接得上，并能传到表达？
2. 什么可以压缩，什么必须保留或按来源取回？
3. 什么预算和触发方式能兼顾质量、等待与调用成本？

前一轮预算调查的记录：当时接口选择 Astra，一次实际成功输入报告16,649 tokens、完整文字请求58,562 bytes；截图中的失败在发送前发生，0次HTTP。现场记录在调查中变化，后来的私有副本已无法精确重现原请求，不能把后续验证称作原现场重放。该阶段的 [发布记录](context-overflow-evidence.json) 保留不变。

当前代码已在同一授权主模型上实现自动语义整理、持久缓存与旧原文查找，默认正文48,000 bytes、完整文字请求64,000 bytes。这是应用字节护栏，不是模型窗口或token数；完整运行流程见 [长讨论自动整理](discussion-compaction_CN.md)。

## 信息组织与优先级

| 内容 | 作用和保留方式 | 压缩规则 |
|---|---|---|
| 长期目标 | 说明用户想发展怎样的关系，简短常驻 | 不把用户愿望写成她的意愿 |
| 当前话题和工作状态 | 这次目的、有效方向、局部限制、未知、进展 | 更新替换旧方向，复用已有状态，避免新建重复状态体系 |
| 当前请求和近期商量 | 理解纠正、选择和“那给一句”等指代 | 当前原话及最新否定/改意图保留；明确被指的候选保留原文和版本 |
| QQ语境和旧事件 | 回应她实际说的事、理解后来的改变 | 加相关证据及必要后续，旧事按需取回，不靠消息条数把全部历史变必需 |
| 关系长期记忆 | 人物自述、共同事情、约定及变化 | 按时间、来源和状态检索；摘要帮助导航，原记录继续可取回 |
| 反馈与方法 | 改善具体建议和适用情景 | 当前选中对象原文优先，旧评价链和方法说明按余量 |

当前代码从有界的近期完整交流、当前请求和适用纠正开始组装，不再补齐最后60条或某个旧检索点之后的全部QQ。最近方向段也受当前交流的间隔与时长边界约束。旧助手建议可通过精确候选、反馈对象或原始turn ID取回；人物资料、旧状态和私下讨论按相关性加载，轻量索引用于发现需补查的来源。这里没有声称所有旧助手全文都建立了独立的向量语义索引，显式选择的大段必要原文仍可能触及护栏。见[按需上下文设计](lazy-candidates-design_CN.md)。

## 已采用的接续方式

采用“当前讨论状态＋近期原文＋按需历史”的接续方式。有必要压缩长篇商量；压缩目标是减小此次模型输入，原始记录留在本机。

先去重复字段、调整可选内容优先级。需要进一步语义压缩时，压旧段并保留一份有覆盖范围和来源版本的讨论记录：有效小目的、局部纠正、已经选定或排除的方案、待交付事项、未决问题、被指代候选的精确引用。对“第二个”“刚才那句”不能只用泛化摘要恢复；选中候选单独保留。

摘要不得成为新的实际QQ事实、分享授权或永久偏好。来源更正、忘记，或话题目的/方向/局部限制变更后，对应记录需失效并从原文重建；仅操作阶段更新不必重压。新整理读取原始轮次，不只反复总结旧摘要。完整来源不必每次全带回，否则只是额外添加一份摘要。程序保存来源版本，模型根据需要查看对应原文。

状态增量继续搭载主回答，不每轮额外调用整理器。仅在预算压力或旧段明显变长时压缩，并缓存到相关来源变化为止。正常商量通常一个主调用；成稿继续保持准备与受限成稿两个阶段；压缩、补查、修复和重试都必须共享一次任务的上限。这些语义整理与来源校验缓存已经实现，首次需要整理后成稿通常3次HTTP，有效缓存后成稿通常2次、回顾通常1次。它们都包括在默认4次HTTP的任务上限中；修复或重试并不另送一份预算。

## 当前实际生效的预算

| 项目 | 当前实现 |
|---|---|
| 上下文正文选择 | 默认48,000 UTF-8字节 |
| 完整序列化文字请求 | 默认64,000 UTF-8字节，包括system、结果schema与JSON转义；图片另有既有边界 |
| 压力条件 | 完整请求达到约82%或组装已经超限，并同时满足相关旧文本/候选量条件；不是仅凭历史条数或可选QQ填满预算触发 |
| 长旧段条件 | 未覆盖的相关旧讨论正文约12,000字节即可考虑整理；压力路径还检查至少约6,000字节旧正文和12,000字节完整候选 |
| 整理结果 | 摘要最多8,000字节，最多12条逐字引用、引用数组最多6,000字节；原文仍存本机 |
| 调用与复用 | 已授权主模型；同一任务默认4次HTTP；缓存按完整scope、来源/轮次指纹、目标/话题、模型目的地与协议校验 |

这些是当前可定位到源码的工程规则，不是tokenizer测得的48k/64k窗口，也不是研究证明的最佳压缩率。真正必须保留的当前输入、QQ或精确反馈对象仍超过预算时，可以明确停止；不为“通过”而静默截断它们。

## 早期Astra token候选设置（未启用）

以下是可试验的工程起点，不是论文最优值，尚未写入运行配置：

| 设置 | 建议 | 验证方式 |
|---|---|---|
| 完整输入软上界 | 尽量在20–32k tokens以内，不为填满预算加无关资料 | 按服务实际usage或对应tokenizer计量，包含system和JSON |
| 完整输入硬上界 | 先用48k tokens作为候选，并为输出、图片和修复留余量 | 校准代理真实能力，不能把字节数等同tokens |
| 压缩触发 | 约达到硬预算70%，或近期原文开始挤掉必需内容 | 48k的70%约33.6k；避免到报错后才启动 |
| 压缩后目标 | 回到约50%，并保近期原话和关键候选 | 约24k，只是防频繁触发的起点 |
| 调用控制 | 普通商量不增加固定整理调用；一次帮助默认最多4次HTTP | 包含压缩、补查、修复、重试 |

近期原文应按预算浮动，而不是把固定6轮当完整性定义；回看历史也应从候选转成相关来源，避免为了用完窗口加入所有旧话题。讨论阶段更重视私下意图和纠正，成稿阶段继续只给获准素材、必要QQ与短表达控制。两阶段不必换两个模型。实际字节护栏仍为48,000/64,000；上表token阈值及70%/50%参数没有生效。自动语义整理已另外按上一节的字节与相关文本条件生效，不应混为同一套参数。

## 一手依据及负结果

- **工程经验**：[Anthropic上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 将compaction与structured note-taking区分，并提醒过度压缩会丢微妙信息。本方案借其分工；它没有验证本项目恋爱效果。
- **论文实验**：[LongMemEval §5.2](https://arxiv.org/html/2410.10813v2) 中，按round组织优于整session的部分设置；用摘要或事实替代原文一般损害细节问答，跨会话推理例外。因此保原文、用摘要导航。这是记忆QA证据，不是自然续聊的直接验收。
- **论文实验**：[PoS §4.3、附录G](https://arxiv.org/html/2610.01415v1) 支持当前有效状态与一致性维护，但RCA-100同一backbone实验总token由355.70K升到1800.13K，约5.06倍。反复自然语言状态也仍有冗余、遗漏和失真风险。因此借鉴状态建模，不照搬每轮Sentinel；人际关系也不要求每轮显示“任务进展”。
- **项目机制**：[fast-jev-compaction](https://github.com/tamaratran/fast-jev-compaction) 删除或缩短工具调用及结果，输出用户和助手文本仍保原文。可借鉴选择和保护规则，直接接入不能压缩本项目长私下文本；本次没有调用Jev或向其发送资料。
- **API机制**：[OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction) 返回供Responses继续使用的opaque compaction item。当前项目走Chat Completions，不能假设本地代理已支持该机制，也不适合把不透明压缩当成可审阅的来源管理。

## 历史窄修与后续实现边界

第一次无损预算窄修已经合并到main并更新桌面助手，当时288项功能检查、28项合成浏览器检查和既有回放通过。更新后的Astra任务用2次HTTP成功完成；QQ未重启、原聊天和草稿保留。原故障输入已变化，验收没有冒充精确原现场重放。

第一次窄修只处理两个可确定问题：未选旧反馈在最近完整私下讨论后按余量加载，当前/明确选中的反馈保留完整对象；模型话题投影不重复传多套来源哈希，程序和原始来源校验保持完整。那个历史阶段没有摘要模型，没有修改运行预算或模型配置。后续实现新增同一主模型的自动整理与持久缓存，保留旧证据并单列新的回放、格式失败和语言质量局限，见 [当前整理实现](discussion-compaction_CN.md) 与 [本轮发布证据](discussion-compaction-evidence.json)。

持续验收“仅去重”与“加入语义接续记录”的收益时，仍应覆盖：长讨论后“那给一句/第二个”、撤销含蓄改直接邀请、旧候选的具体反馈、连续压缩后的来源更正/删除、同一联系人多次切换话题。若丢目的、否定、候选身份或分享边界，即使压得更短也不通过。若去重已同样可靠且更便宜，就没有证据增加摘要调用。实际关系效果另从双方真实互动观察。
