# 组件设置：原始证据之间的关系判断

这一路已经提供可运行的契约、CLI 与显式 Luna 适配器：`scripts/eval-memory-decisions.cjs`、`scripts/eval-memory-decisions-luna-adapter.cjs`，初始数据在 `evals/memory-decisions/`。当前是 **8 组对照、16 例可见开发样本**。本组件 worker 仅运行合成和注入 fetch 检查；父协调者如另行运行真实试点，结果须以独立工件为准。

## 和端到端设置的区别

| 项目 | 本组件设置 | 项目端到端回放 |
| --- | --- | --- |
| 起点 | 固定的新旧原始证据、来源时间和可用性事件 | 原始 QQ 与用户操作按声明条件进入软件 |
| 可以控制什么 | 提供给判别器的候选证据集合 | 外部输入、时间与用户可观察操作 |
| 谁建立记忆 | 不建立产品记忆，只输出受控关系诊断 | 被测软件自行抽取、维护和读取 |
| 没测到什么 | 召回、调度、压缩、状态提交、后续聊天效用 | 需要通过轨迹再定位具体组件原因 |
| 结论 | 在相同证据条件下，判断是否可靠、调用是否划算 | 整条软件链路是否持续提供可靠帮助 |

固定候选输入在组件诊断里是合法条件，但不能把这些候选、参考答案或预期人物理解直接塞入端到端模型输入。特别是撤回样本：本组件明确提供“曾经看到什么”的历史材料以及后来撤回事件；这不等于端到端系统在撤回之后仍可重新读取那个原文。

## 为什么没有一个强制互斥的关系标签

主体是否相同、描述的时间范围是否相同、内容关系及证据是否充分是四个不同问题。两条材料既可能补充细节又涉及时间变化；说话的人相同，也不代表谈论的人相同。后到的报告不自动代表世界状态更新。

输出契约因此采用四个轴：`same_subject`、`time_scope`、可多选的 `relationships`、`evidence_sufficiency`。允许 `uncertain`、`unknown` 和 `not_applicable`，不要求判别器替程序执行更新。`output.schema.json` 是枚举与字段形状的唯一来源。

参考标注全部标记为 `provisional_ai_reference`。它们只是待独立核对的候选解释，CLI 没有把它们转成自动通过率。现有父项目评分标准和案例都未被改写。

独立原始数据审查后，参考修订为 `provisional-ai-v2`：同一事件后来补充日期仍可判相同时间范围；没有新内容命题的撤回操作可用 N/A；部分证据失效与全部必要支持不可用要分开。证据充分性指“足够判断两条说法的关系”，不是“足够选定哪条世界事实是真的”。原 v1 标注、公共契约和所有 raw runtime 哈希已单独保存；本次不改原始事件，也未查看真实模型输出来调标签。公共轴说明有独立修订号及新契约哈希，旧真实试点仍绑定旧输入，保持未评分。

## 原始数据怎样进入判别器

本批以项目内虚构原始历史为种子，逐条记录来源路径、case/event ID、源文件哈希和改造说明。不存在把原有 `understanding` 笔记当作真实事实喂入的问题；没有声称已经适配 HaluMem、LongMemEval 等公开数据。

真正交付给 adapter 的字段只有任务、截止时间、新旧观察、可用性更新和公共输出契约。原始来源 ID 转为 `s#`，可用性事件转为 `u#`；case、family、来源改造说明和参考判断都不进入判别输入。时间、主体、渠道和逐字内容保持在受控输入里。

## 已经能执行的检查

```bash
node scripts/eval-memory-decisions.cjs --check
node scripts/eval-memory-decisions.cjs --list
node scripts/eval-memory-decisions.cjs --id md-temporary-or-stable-temporary --view model
node scripts/eval-memory-decisions.cjs --id md-temporary-or-stable-temporary --view review
node --test --test-isolation=none tests/eval-memory-decisions.test.cjs
```

默认只列清单。离线导出不加载 adapter。另有显式 `--adapter` 的执行协议，能保留真实返回对象、失败、时限、输入/数据/契约/adapter 身份和未填写的评审表；合成适配器只验证调用边界。它不绕过 QQ 软件后就给自己标上 E2E。

Luna 适配器要求显式 `--live --settings-file <已有Luna配置文件>`，复用当前选中 profile 的只读解析，且核对模型名确实为 Luna。每次判别最多一次 HTTP；失败也计入全局 `--max-http`，没有自动重试或修复。请求、原始响应、用量、时限、目的地、配置哈希和漂移检查均会保留，密钥值被遮盖。它不会修改全局 profile 或 provider。测试中的注入 fetch 被标为合成证据，不能宣称真实模型验证。

## 仍待实施与质疑

1. **参考标注校准。** 需要独立核对人物、时间与条件，保留分歧；样本少时不能谈可靠的置信度校准。
2. **真实判别证据。** Luna bridge 已具备受控执行入口，但本 worker 没有发起真实请求；JEV bridge 尚未接入。实际结果、provider 错误和用量需要另行保存；成功调用不能等同判断正确。
3. **真实输入长度与候选来源。** 本设置把候选集合固定，比较 JEV 与 Luna 时有利于归因，但不能证明产品检索能找到这些候选；必须与正常端到端结果并排报告。
4. **候选类别未必足够。** 若真实输入需要“不同活动但同一人”“证据对事实足够、对当前状态不足”等更细解释，应先记录遗漏，不强迫输出一个虚假的确定标签。
5. **组件更快不保证产品更快。** 若 Luna 原本一次完成抽取与关系判断，新增 JEV 只是额外串行请求，必须看完整维护与下游延迟，而不是只比单次模型响应。

本 worker 尚未运行真实判别、自动评分或自动优化；产品代码、已有父项目数据、全局模型配置与真实 QQ 均未修改。已有 19 项组件／适配器检查通过，全部使用固定或注入传输，其中含真正的独立进程 CLI 调用，防止“导入 main() 的测试通过、实际命令行却失败”。

真实试点冻结之后另补了初始化故障留档：adapter 模块加载、factory 抛错或超时、身份不符都保留 manifest 和“未派发输入”的不完整案例。未观察到 HTTP 数量时保持未知，不能从零次判别调用推断零次网络请求；初始化失败也不被当成模型质量失败。此前冻结工件没有重跑或改写。
