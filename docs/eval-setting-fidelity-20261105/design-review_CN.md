# 场景匹配、评测设置与实施审查

状态：设计审查与首批离线实现。用户选择端到端和组件设置同时准备、分别报告。本文不激活 Goal，不宣布模型质量通过，也不把 JEV 接入作为既定产品改动。

## 1. 如何确认测的是这个项目

匹配不是靠在提示词里写“你是 QQ 助手”，而是固定外部经历和用户求助，让实际产品自己执行：

```text
虚构原始 QQ / 私下用户请求 / 笔记及权限 / 来源更新 / 用户控制 / 时间
                                  ↓
                  可替换 adapter 的外部输入边界
                                  ↓
     实际 Controller → Store / 正常记忆维护 → 检索 / 上下文组装
                                  ↓
               实际模型 adapter / 实际序列化请求
                                  ↓
                 完整可见回答、记忆公开视图、后续反馈
```

当前测试替换 QQ 的原生 IPC 输入，用虚构 native-shaped 实收/实发消息驱动真实归一化与 controller。后端 HTTP、模型适配器、Store 和上下文代码参与执行。默认合成模型只检查这条链路；显式 live 才有模型语义输出。两者均不是实际 QQ 桌面验收。

## 2. 三种设置必须分开

| 设置 | 初始输入 | 实际测量范围 | 不能宣称 |
| --- | --- | --- | --- |
| 空库顺序事件流 | 空库，从时间起点逐条引入 QQ、用户请求、笔记、控制和显式空闲 | 这些经历经正常产品调用形成状态、记忆及后续回答的过程 | 尚不覆盖模型进行中并发新消息、切联系人或重启持久化；虚拟等待不是实际桌面耗时 |
| 历史检查点回放 | 给定截止时点可见的原始 QQ、归档私聊、用户笔记，由本版本重建派生状态 | 给定历史与已声明准备过程下的后续行为 | 不代表过去的私下请求、任务、经验、压缩状态曾按历史逐步执行；主动预整理不证明正常调度 |
| 组件诊断 | 同一套受控新旧原文、候选或真实输入快照 | 给定这些输入，关系判别等组件的局部能力 | 不代表产品自己能找到候选或最终回答有用；不能替代 E2E |

同一场景可以有多个设置，但必须有独立 ID、准备条件、输入哈希和结论。不要悄悄把一份检查点历史转换成从空库历史。

## 3. 什么可以“注入”

端到端可引入普通外部行为：实际 QQ 双方发言、用户私下请求、用户明确撰写的近况或偏好笔记、授权变化、来源撤回及独立时间条件。它们带原始说话者、时间、来源 ID 和用途。

下列内容不能预先写进 E2E 的产品状态：期望人物画像、gold memory、正确的新旧关系标签、标准答案、应做/不应做说明、另一个版本抽出的记忆、提前选出的正确上下文。产品必须从原始来源形成自己的派生状态。

组件可以接受受控候选或旧理解，但必须明确：这是输入前提。标注来源、时间、主体和原文，保留未知与多种合理解释；组件判别通过不等于生产检索通过。

归档助手文字仅在检查点设置中作为已给定历史。新事件流里的助手回答必须由运行中的产品生成。针对“上一句”的反馈必须绑定真实生成的 reply ID；无法绑定则报告未回放，不替换为预设成功答案。

## 4. 独立审查提出的反方问题

### P1：原文恢复完整，会不会被误当成完整历史执行？

会有这个风险。原 adapter 的 `restorePrivate()` 直接恢复双方历史文字，没有执行每条旧用户请求对应的 `/api/assistant`，也不会重演当时所有 task/experience/compaction 转换。

处理：保留检查点用途，准备回执明确 `entire_history_reexecuted:false`，分别列归档用户/助手和笔记数量。新增空库事件流用于历史执行问题，不要求其状态与归档检查点相同。

### P1：后台完成究竟指什么？

`pending=0` 只表示来源 journal 已处理，还可能有 `semanticPending`、`pendingProposals`、恢复工作或错误。正常请求也可能中断后台维护。

处理：记录完整准备前后 memory status；固定事件时间提问，在显式空闲区间给正常调度有上限的原生完成机会。未完成作为条件保留，不注入空记忆或等到成功才开始计时。

### P1：源码/配置指纹是否覆盖实际输入？

审查发现历史 backend hash 仅覆盖 `.cjs`，没有涵盖协议 JSON；配置白名单漏了产品实际使用的 `memoryInputBytes`。工厂创建后源码变化也可能使身份和实际加载版本不同。

处理：不改历史 hash 算法，另加 contract JSON identity；记录有效非秘密配置和隔离覆盖项，保留记忆请求预算；每次创建 episode 前验证源码/协议未漂移。

### P2：是不是给了 JEV 不公平的“正确旧记忆”？

局部判别时可以给 Luna 和 JEV 相同候选以隔离能力，但这是组件条件。若组件正确、E2E 失败，再检查候选召回、实际交付与生成使用，不能据此直接提高写入权限。

关系标签允许分轴或多个兼容解释。产品行为标准不要求某个内部 transition 或固定记忆格式。

当前组件实现是一个**候选语义判别任务接口**，尚未替换生产 `memory-engine` 的整批提案，也没有连接 JEV。Luna 能执行这个受控任务，不等于其结果已经可以由生产写入器安全消费。真正接入时还要核对候选检索、原文闭包、实际 Store 版本目标和提交权限；不能直接把 benchmark 标签当作写入指令。

### P2：快的局部调用是否让完整系统更快？

不一定。一次 Luna 维护可能同时做抽取和关系判别；若 JEV 只是额外串行调用，成本与延迟可能增加。

处理：分别测固定输入的判别时延和完整整理耗时，记录批大小、缓存、网络/重试、Luna 回退与回答成本。最终回答模型保持相同，不先假定 JEV 优于原方案。

### P2：顺序流是不是已经测试所有真实竞态？

不是。等待每次回答完成再输入下一事件，不覆盖推理期间收到新消息、撤回或切联系人的情况。该类问题需要独立的并发集成探针，不能从顺序 E2E 的绿色结果推出。

## 5. 实施顺序与责任边界

1. 准备回执与身份：验证原始输入如何恢复、记录实际整理和调用、保留失败与未完成；只做工程归因，不打质量分。
2. 同时准备空库顺序流和组件诊断，各有独立数据契约及 CLI。离线先验证 reviewer-only 隔离、事件顺序、真实输出保留和调用边界。
3. 本地案例提供 QQ 特有权限、实发和连续商量种子；公开数据另做取材/许可/角色映射审查。当前并不声称已导入 HaluMem 等完整公开数据。
4. 冻结一批对照历史、实现、配置、模型和预算，再用 Luna 做真实回放。保留默认合成检查作为集成证据，不给它补填语义评分。
5. 端到端先沿用现有 `assistant-help-v1` 和外部 case criteria。此前五维/0–2 分是讨论草案，不悄悄替换当前 rubric。新增/改变 Judge 或 rubric 时另做盲化校准。
6. 对实际输出独立盲审；源码诊断与质量评审分开。JEV 初期可以是非破坏性的影子关系判断，是否替代现有步骤由证据决定。

## 6. 证据分级

- 数据校验：契约可读、原始时间/ID 合法；无语义成绩。
- 合成产品集成：真实后端被驱动，provider 替换；无模型质量成绩。
- 真实模型回放：实际输入/输出、成本和失败已保留；仍需独立评审。
- 桌面集成：真实 QQ、窗口、原生事件与交互的单独证据；本轮未执行。

已做针对性历史检索和一次独立架构审查。历史材料仅用于导航；机制和缺口按当前源码核对，旧测试数量和部署记录不作为本轮效果证据。

## 7. 数据审查追加

独立数据审查未查看实际 Luna 输出，先检查种子与暂定参考。16 个组件案例的源文件哈希、源 case/event ID、原始文字、时间及说话者一致；4 个流式案例的来源 ID 和已披露改造也可核对。单独的 `seed-provenance-audit.json` 记录该项检查，不把来源一致性当作语义标注正确。

审查发现若干暂定标签过窄：不同日期的局部请求不必具有同一适用范围；旧活动后来补充日期不必仍标 unknown；只有部分接受证据撤回时不应自动把全部支持视为失效；没有新内容命题时“不适用”不同于“主体不确定”。此外，一对日期反例同时改变了证据确定性，不能作为单一时间因素的因果对照。

组件实现者与审查者据原文澄清共同定义并保留参考修订记录，未按模型实际答案调整标签。原始 live pilot 绑定旧的未评分契约/数据身份；后续参考修订和来源元数据补充另记版本，不覆盖旧结果。暂定参考仍需独立校准，不能据此直接公布准确率。
