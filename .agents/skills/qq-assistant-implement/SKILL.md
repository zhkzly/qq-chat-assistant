# QQ assistant implementation

Work toward a purpose-driven, long-term assistant that maintains raw evidence, durable memory, current intent and state, applicable methods, selective context, and feedback. The user should be better able to understand a situation, choose the next step, find real talking material, initiate or continue conversation, share themselves, and build shared experiences. Romance is the current application, with arbitrary later purposes supported. Improve the actual product across these abilities; better wording or green development cases alone are insufficient.

Consume the coordinator's causal hypothesis, round identity, acceptance conditions, and assigned ownership. Analyze the frozen dataset trajectories and inspect the complete affected product path. Implement one coherent candidate that resolves the supported cause; a complete fix may rewrite components across ingestion, storage, memory, state, context, model, UI, and adapter. A small comparison batch and stage label do not restrict the architecture or editable components. Coordinate ownership changes before editing files assigned to another worker; do not revert their work. Preserve the ordinary desktop QQ plus separate assistant window workflow, account/contact binding, string QQ IDs, and manual copy/send boundary. Never send, forward, auto-reply, or simulate QQ send keys. Drafts and clipboard actions are not actual sends.

For design and implementation, retrieve relevant OpenViking experience and primary web sources when they address a concrete uncertainty. Explain applicability and limits against actual product consumers, state, lifecycle, and counterexamples; do not adopt an architecture merely because a paper proposes it. Cooperate with the coordinator's on-demand `qq_architecture_reviewer` before major implementation and after the candidate; its critique does not replace independent actual-output evaluation.

Own product code and its replaceable replay adapter. Do not change frozen raw cases, behavioral criteria, rubrics, calibration references, reviewer ratings, or earlier evidence to improve a result. A genuinely faulty case requires a separately reviewed dataset correction and a new freeze; report it to the coordinator. Keep real chat records and credentials out of Git and evaluation artifacts.

For context selection, understanding, continuity, or suggested wording changes, start with `npm run eval:check`, then choose affected cases using `npm run eval:list` and `npm run eval:replay:list`. Preserve the full 38-case, 81-step dataset. The first diagnostic comparison has 4 cases and 7 steps; it is an initial evidence batch, not the final acceptance set or the product goal. Later coverage must include active-topic initiation, reconnecting, and sustained consultation. Broad memory, context, or global-prompt changes require relevant long-history, local-correction, and closed-topic checks before acceptance, with further coverage determined by impact. Report a recurring failure to the coordinator so it can revise the causal hypothesis. Read `evals/assistant/REPLAY.md` before changing the adapter or replay conditions. Keep product imports and derived memory formats inside the adapter; rebuild state from the frozen raw prefix for each implementation.

Run focused functional checks and relevant replay into new directories. The default synthetic transport supplies integration evidence only. Use `--live` only within explicit model-call authorization and its global HTTP cap. Do not claim a conversational gain from a build, mock, inspection export, or synthetic transport. Preserve actual outputs, errors, missing steps, transport evidence, and run diagnostics for the coordinator; leave semantic ratings ungraded for the separate evaluator.

Return the changed files, relevant checks and exit codes, replay artifact locations, implementation identity, and remaining failures or uncertainty. Explain the product behavior and evidence limit without prescribing the evaluator's verdict. Do not activate the Goal, commit, publish, modify global configuration, or broaden the task's authorization.
